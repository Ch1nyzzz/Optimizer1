2. Organized 如何管理 trace 与 modification

organized optimizer 的核心不是把更多历史文本塞进 prompt，而是把优化过程拆成两类结构化证据：一类回答“候选表现如何、哪些任务变好或变坏”，另一类回答“proposer 到底改了什么、什么时候改、改过哪些文件”。两类证据都写入同一个 RunStore，但通过不同工具命名空间暴露给 proposer。

Trace / evaluation evidence

这部分管理 evaluation side 的事实：iterations、candidates、task results、passrate、average score、token consuming、frontier 和 task-level outcome。它回答“某个 candidate 是否真的有效”。 

RunStore tables:
  iterations
  candidates
  task_results
  frontier_members
  state_snapshots

Tools:
  runstore_trace_iteration_meta
  runstore_trace_candidate_outcome
  runstore_trace_compare_iterations
  runstore_trace_task_history
  runstore_trace_frontier

Modification evidence

这部分管理 proposer side 的事实：proposer call、diff、changed files、file access、proposal metadata 和相似修改。它回答“模型基于什么证据做了什么代码改变”。 

RunStore tables:
  proposer_calls
  iteration_diffs
  file_accesses
  proposals
  proposal_outcomes

Tools:
  runstore_mod_iteration_diff
  runstore_mod_proposer_call
  runstore_mod_file_history
  runstore_mod_similar_changes
问题 pure default no-trace organized
历史状态在哪里 主要散落在 summaries、reference iteration bundles、raw artifacts 和 prompt narrative 中。 RunStore 是主状态；state.md 是 RunStore 生成的轻量 snapshot。
怎么查候选表现 模型自己读 JSON/summary，或者从 prompt 里的历史描述推断。 通过 trace tools 查询候选 outcome、iteration compare、task history 和 frontier。
怎么查改动历史 模型读 diff 文件和 reference source snapshot，自行拼接上下文。 通过 modification tools 查询 iteration diff、proposer call、file history 和 similar changes。
summary 的角色 是主要历史载体之一，容易变成 summary-driven loop。 降级为 debug/export；organized proposer 不以 summaries 作为主状态。
可审计性 需要从多个 artifact 反查。 每轮可以沿 RunStore 回答：看了什么、改了什么、候选表现如何、是否进入 frontier。

这次 fixedtools 版本还记录了 proposer 证据使用指标：RunStore tool calls、raw trace reads、raw reference reads、raw summary reads。最终四个 organized runs 的 raw_summary_file_reads 都是 0，说明已经不再依赖 summaries 作为主历史；同时 RunStore tool calls 非零，说明 trace/modification 工具确实被模型调用。

当前设计保留 raw trace/reference 作为 fallback。也就是说 organized 不是 tool-only；它的约束是“RunStore 是 source of truth，tools 是精确查询接口，raw artifacts 是可读证据备份，summaries 不参与核心决策”。

3. 这次对照里的 Pure Default 是什么

这里的 pure default no-trace 指本次重新启动的无 trace-tool 对照，不是之前误启动的 trace-enhanced default。它的核心属性如下：

  • --selection-policy default。
  • 不启用 --organized，没有 generated state.md 作为 state contract。
  • 不注册 RunStore MCP tools，不注册 trace-tools 给 proposer 使用。
  • proposer 主要依赖默认 prompt、当前 workspace、历史 summary/debug artifact 这类传统上下文。
  • 没有将查询接口分成 trace evidence tools 与 modification history tools。

4. Organized 算法结构有什么区别

organized 版本的目标不是简单“给模型更多文本”，而是把优化循环从 summary-driven loop 改成 structured evidence loop：

Pure default loop

workspace
  + loose history / summaries
  + proposer
  + evaluator
  -> candidate

历史信息主要以文本总结或文件 artifact 的形式进入 proposer。模型如果要追溯某次修改、某个任务失败历史、某个候选的 diff，需要自己在文件系统里找。

Organized loop

RunStore
  -> generated state.md
  -> RunStore MCP tools
  -> autonomous proposer
  -> evaluator
  -> RunStore records outcome

RunStore 是主状态，state.md 是当前 snapshot，tools 是精确证据查询接口。summaries 不再作为 proposer 的主状态来源。

3.1 RunStore

RunStore 负责组织每一轮优化历史，包括 iterations、candidates、eval results、task traces、proposer calls、diffs、file accesses、frontier 和 proposal metadata。它的作用是把“历史叙事”变成可查询的结构化状态。

3.2 state.md

state.md 由 RunStore 生成，只描述当前轻量状态，不写 suggested queries、diagnosis 或 next action。当前版本只保留 run metadata、最大化 passrate 的目标、recent top-5 passrate frontier，以及可用 RunStore tools；它不再暴露 current base，避免 default policy 下的 state base 被误解为 patch base。

3.3 RunStore MCP tools

这次修复后，proposer agent frontmatter 明确 allowlist 了实际 Claude MCP tool 名称，例如： 

mcp__runstore-tools__runstore_trace_iteration_meta
mcp__runstore-tools__runstore_trace_candidate_outcome
mcp__runstore-tools__runstore_trace_compare_iterations
mcp__runstore-tools__runstore_trace_task_history
mcp__runstore-tools__runstore_trace_frontier
mcp__runstore-tools__runstore_mod_iteration_diff
mcp__runstore-tools__runstore_mod_proposer_call
mcp__runstore-tools__runstore_mod_file_history
mcp__runstore-tools__runstore_mod_similar_changes

我们刻意区分了两类工具：

工具类别 用途 例子
Trace / outcome tools 查询评测结果、任务历史、候选对比、frontier。 task_history, candidate_outcome, compare_iterations, frontier
Modification tools 查询 proposer 做过什么修改、diff、文件演化、相似修改。 iteration_diff, proposer_call, file_history, similar_changes

3.4 proposer 自主性

prompt 没有强制模型必须调用某个工具，也没有把 next action 写死。模型可以读 raw traces/reference 作为 fallback，但它被明确告知：需要精确历史证据时优先使用 RunStore tools；如果绕过 tools，应该在 hypothesis/changes 里说明原因。

9. 为什么 LongMemEval-S organized 没超过 pure default

  • top_k 路线差异：pure default 的强候选主要是 top12，例如 mmr_chrono_evidence_top12 和 weighted_overlap_mmr_top12。organized 两组最终大量落在 top8，test recall 可能不足。
  • train overfitting：organized-pareto-nohist train 到 0.72，但 test 只有 0.55，说明 temporal/specificity/enumeration 类策略抓住了 train pattern，但泛化不如 pure default 的 weighted-overlap MMR。
  • tool 使用不是主要瓶颈的唯一解释：修复后 tools 已经被用，summary reads 为 0，但模型仍大量读 raw evidence。结构化工具提高了可追溯性，却不自动保证搜索方向更泛化。
  • pareto selection 的副作用：pareto/no-historian 更愿意探索 token / passrate frontier，LongMemEval-S 上推高了 train frontier，但 test frontier 没追上 pure default。

10. 当前判断

问题 判断
organized 架构是否已经生效？ 是state.md 有内容，MCP tools 在 allowlist 中，RunStore calls 被记录，summary reads 为 0。
organized 是否全面优于 pure default？ 不是LoCoMo pareto-nohist test 更好；LongMemEval-S pure default test 仍更好。
目前最有价值的 organized 结果是什么？ LoCoMo organized-pareto-nohist fixedtools：test 0.3823，相比 pure default 0.3616 有正收益。
最明显的问题是什么？ LongMemEval-S organized-pareto-nohist train 0.72 但 test 0.55，存在明显泛化差距。
下一步该优先改什么？ 保留 RunStore/state/tools；在 selection/prompt 层增加对泛化风险、top_k 路线、test-like diversity 的约束，而不是回退到 summary-driven。
